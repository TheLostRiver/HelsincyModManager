# 应用内更新器规划

本文档说明 Helsincy Mod Manager 为什么在 Alpha 阶段不提供应用内自动更新，
以及后续引入时必须先解决的前置条件。

当前状态：**未实现，且 Alpha 阶段不计划实现。**

## 当前的更新方式

`0.1.0-alpha.0` 起，「关于」页提供手动更新入口：

- 「检查更新」打开 GitHub Releases，用户自行对照版本号并下载发布包。
- 「更新记录」打开 `CHANGELOG.md`。
- 页面明确写出「当前尚未启用应用内自动更新」，不暗示存在后台更新。

Release notes 必须写明本版本无自动更新、后续版本需手动下载，避免用户等待不存在的推送。

## 为什么 Alpha 阶段不引入

Tauri updater 的签名机制带来一个**不可逆**的决定：更新包由私钥签名，公钥编译进应用。

一旦某个版本携带公钥发布出去：

- 后续所有版本必须用同一把私钥签名，否则已安装的客户端拒绝更新。
- 私钥丢失等于所有已安装用户永久失去升级能力，只能引导手动重装。
- 更换密钥需要用户手动安装一次过渡版本，Alpha 用户规模下这个代价不划算。

在以下条件都未满足前引入 updater，风险大于收益：

- 尚无平台签名策略（见 `docs/release/发布与产物说明.md`：「还没有平台签名策略」）。
- 尚无发布 CI 的密钥注入与轮换方案。
- 首个版本的发布流程本身尚未经过实际验证。

因此正确顺序是：Alpha 手动更新 → 发布流程跑顺几个版本 → 确定密钥管理 → Beta 阶段引入 updater。

## 引入前必须先解决的问题

### 密钥管理

- 私钥生成方式与保管位置，且不得进入版本管理。
- 私钥备份策略：丢失后果是永久性的，必须有离线副本。
- CI 中通过什么机制注入，如何避免出现在日志里。
- 轮换流程，以及轮换时已安装用户的迁移路径。

### 更新源与清单

- 更新清单托管位置（GitHub Releases 附件或独立端点）。
- 预览通道与稳定通道是否共用同一清单。
- 版本号比较规则如何处理 `-alpha.N` 预发布标识。

### 安全边界

- updater 的网络访问必须纳入 CSP 与 Tauri capability 白名单，不能放开为任意域名。
- 权限范围与现有 `opener:allow-open-url` 的收紧策略保持一致，不因更新功能放宽整体网络访问。
- 更新过程不得触碰游戏目录、Mod 库或存档；应用自身更新与玩家数据操作是两套独立路径。

### 用户可控性

- 是否允许用户关闭自动检查。
- 是否允许跳过某个版本。
- Alpha/预览通道用户是否默认接收更新。

### 失败与回退

- 下载或校验失败时的行为，不得使应用进入无法启动状态。
- 更新失败后如何回到可用版本。
- 正在执行安装、卸载、备份任务时收到更新请求的处理方式：应拒绝而非中断任务。

## 与安全策略的一致性要求

`docs/TESTING.md`「发布与打包」章节要求人工确认「自动更新策略是否与安全策略一致」。

在 updater 落地前，该项的确认结论是：**当前无自动更新，不存在与安全策略冲突的更新路径。**

updater 落地后，该项必须改为实际验证签名校验、清单来源限制和权限白名单。
