# 发布与产物说明

本文档定义 Helsincy Mod Manager 的发布策略、平台支持等级和产物命名规则。当前项目仍处于脚手架前阶段，因此本文档是发布规划基线，具体构建产物会在 Tauri 工程落地后补充。

## 发布目标

第一阶段目标：

- Windows 为首发和主要支持平台。
- Linux 作为后续实验性平台。
- Steam Deck Desktop Mode 作为 Linux 实验性验证目标。
- macOS 暂不作为一等支持目标。

## 平台支持等级

### Tier 1：主要支持

Windows x64。

要求：

- 能安装和启动桌面应用。
- 能识别或手动选择 MHW:I 游戏目录。
- 能导入、校验、安装、卸载 Mod。
- 能备份和恢复测试存档目录。
- 能通过最小 smoke test。

### Tier 2：实验性支持

Linux x64。

要求：

- 能启动桌面应用。
- 能手动选择游戏目录。
- 能执行不依赖 Windows API 的核心功能。
- Steam library 扫描可逐步完善。

### Tier 3：社区验证

Steam Deck Desktop Mode。

要求：

- 通过社区测试反馈确认是否可用。
- 不在没有实机验证的情况下承诺稳定支持。
- 发布说明必须标注实验性状态。

## 发布类型

### Alpha

用于早期功能验证。

特点：

- 允许功能不完整。
- 允许 UI 尚未稳定。
- 必须避免破坏真实游戏目录和真实存档。
- 发布说明必须列出已知风险。

### Beta

用于接近完整工作流的验证。

特点：

- 主要功能应能串联。
- 必须有安装、卸载、回滚、备份的基础测试。
- 可以接受少量已知问题，但必须有规避说明。

### Stable

用于推荐普通玩家使用。

特点：

- 不应存在已知的误删、错误覆盖、错误恢复问题。
- 必须有明确的版本号、变更说明和回滚建议。
- 必须通过发布检查清单。

### Nightly / Preview

用于开发过程中的非正式验证。

特点：

- 可以由 CI 自动生成。
- 不保证稳定。
- 不建议普通玩家使用。
- 不应覆盖正式 Release 产物。

## 版本号规则

计划采用语义化版本：

```text
MAJOR.MINOR.PATCH
```

示例：

```text
0.1.0-alpha.1
0.2.0-beta.1
1.0.0
```

含义：

- `MAJOR`：破坏性变化或重大架构变化。
- `MINOR`：新增功能或较大行为变化。
- `PATCH`：修复问题、补充测试或文档修正。

在 `1.0.0` 前，`0.x` 版本允许更频繁调整接口和数据结构，但涉及安装清单、备份格式、数据库 migration 的变化必须写明兼容性。

## 预期产物命名

产物命名应包含：

- 应用名
- 版本号
- 平台
- 架构
- 渠道

示例：

```text
HelsincyModManager-0.1.0-alpha.1-windows-x64-setup.exe
HelsincyModManager-0.1.0-alpha.1-windows-x64-portable.zip
HelsincyModManager-0.1.0-alpha.1-linux-x64.AppImage
```

最终命名以 Tauri 打包能力和 CI 实现为准，但不应频繁变动。

## Release 附件策略

正式 Release 应至少包含：

- Windows 安装包。
- 校验文件。
- 变更说明。
- 已知问题。
- 升级和回退注意事项。

后续可选：

- Windows portable 包。
- Linux AppImage。
- SBOM。
- 签名文件。

不应上传：

- 第三方 Mod 包。
- 真实玩家存档。
- 本地配置文件。
- 含 token、cookie、API key 的日志。
- 未脱敏路径截图。

发布时应同步更新根目录 `CHANGELOG.md`。

## 发布说明模板

发布说明至少包含：

```text
版本：
发布日期：
发布类型：
支持平台：

新增：
修复：
变更：
已知问题：
升级注意：
验证范围：
```

涉及安装、卸载、备份、回滚的版本，必须额外说明：

- 是否修改安装清单格式。
- 是否修改备份格式。
- 是否修改数据库 schema。
- 是否需要玩家重新扫描 Mod 库。

## 发版前检查清单

发版前至少确认：

- 工作区干净。
- 版本号已同步。
- README 和相关文档已更新。
- `docs/TESTING.md` 中对应范围的测试已执行。
- 没有提交真实 Mod 包、真实存档或敏感信息。
- 安装、卸载、回滚相关变更有测试或手动验证说明。
- Release notes 写明已知风险。
- 实验性平台明确标注实验性。

## Steam Deck 说明

Steam Deck 支持必须谨慎描述。

在没有实机验证前，只能写：

```text
Steam Deck Desktop Mode experimental / planned
```

不能写：

```text
Steam Deck fully supported
```

如果后续通过社区测试，也必须在 Release 说明中写明：

- SteamOS 版本。
- 测试者使用的安装方式。
- 游戏安装位置。
- 是否使用 SD 卡。
- 已知 UI 或权限问题。

## Windows 后台 Worker 产物门禁

Windows Tauri bundle 必须同时包含 GUI 主程序和同目录 sibling `hmm-save-backup-worker.exe`。仓库中的准备脚本会先生成 `src-tauri/binaries/hmm-save-backup-worker-<target-triple>.exe` 供 Tauri `externalBin` 消费；该 target-triple 源产物属于生成物，必须保持 ignored，不能提交。

以下是三个独立 gate，不能相互替代：

1. 构建 gate：dev/release sidecar prepare 成功，Tauri 选择 `hmm-tauri` 作为主程序。
2. 安装态 gate：在一次性 Windows 账户或 VM 安装 bundle，确认 sibling worker 存在并完成受控 Scheduled Task smoke/cleanup。
3. 卸载 gate：NSIS 和 WiX 分别验证自动移除 owned Scheduled Task、不删除 foreign task，并覆盖 running task、升级、repair 和静默卸载。P7.2c helper、双 sidecar、NSIS hook、WiX custom action 和 static/build gate 已完成；`0.1.10` 已完成 WiX 核心卸载、upgrade/repair、最终 owned 卸载与 NSIS payload 尾部矩阵。首次运行修复的新候选仍需复验 NSIS 自动收敛、owned 卸载和 running fail-closed，runtime gate 尚未结束。

MSI/WiX 不接受包含非纯数字预发布标识的应用版本；正式 MSI 构建前必须使用兼容版本并保持 `package.json`、Tauri config 和 Rust crate 版本一致。

## 当前状态

当前已有 Tauri 工程、Rust workspace、前端构建和 Windows worker sidecar 准备脚本，但仍没有可发布的 Stable 产物：

- P7.2a sidecar 构建配置已落地，target-triple 生成物不会进入 Git。
- P7.2b 应用级全局启停、SQLite 用户意图、Settings/Profile 状态和 fail-closed 退出提示已落地；这只证明应用 contract 与自动化门禁，不替代安装态 gate。
- MSI 构建验证继续使用未提交的纯数字版本覆盖文件；项目版本文件仍保持 `0.1.0-alpha.0`，正式发布前必须采用兼容 MSI 的纯数字版本并统一版本来源。
- NSIS 与 MSI debug artifact 已生成并完成 payload/sequence 检查；仅在 disposable Windows Sandbox/VM 安装和运行，不在开发者账户执行。
- P7.2a Windows 安装态 sibling worker、真实 Scheduled Task、fresh heartbeat、synthetic automatic backup 与受控 cleanup 已于 2026-08-07 认证。
- P7.2c 已实现独立无参数 cleanup helper、NSIS PREUNINSTALL、WiX pre-`RemoveFiles` user-context custom action；`0.1.10` 已通过上述大部分 runtime 矩阵，新候选仍需关闭首次运行修复的最终 NSIS gate。
- 还没有 GitHub Actions 发布流程。
- 还没有平台签名策略。

因此不能仅凭本地 release binary 或 fake tests 宣称 Windows runtime acceptance。
