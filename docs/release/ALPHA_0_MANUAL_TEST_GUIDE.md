# Alpha 真机验收操作指南

配合 `ALPHA_0_ACCEPTANCE.md` 使用。前者是勾选清单，本文说明**怎么测、记什么、
日志怎么用**，以及哪些坑会让验收结论失效。

## 一、开始前必须做的四件事

### 1. 先开 Debug Log

Debug Log **默认关闭**，而它是诊断价值最高的一类。如果不开，事后回看只有 App/Task/Audit
三类，很多细节无法复原，等于白测一轮。

入口：设置页 → Debug 日志开关（`set_debug_log_settings`）。

开启后确认写入 `%APPDATA%\dev.helsincy.modmanager\logs\debug\debug-YYYY-MM-DD.log`
（应用标识是 `dev.helsincy.modmanager`，不是产品名）。

### 2. 隔离测试数据

- 游戏目录用**可丢弃的副本**，不要用你在玩的本体。
- 存档目录同样用副本。
- 在副本之外**再做一份外部备份**，不要把被测程序自身的备份功能当唯一保险。

理由：本次验收覆盖游戏目录写入、覆盖、删除和存档恢复。这些路径出 bug 的后果是数据丢失，
而 Alpha 的这些路径恰恰是第一次真机跑。

### 3. 记录环境基线

写在验收单顶部，出问题时这些是复现前提：

- Windows 版本号
- 显示缩放（你的环境是 4K + 150%，CSS 视口约 1792px）
- 游戏版本与来源（Steam / 其他）
- 是否有其他 Mod 管理器装过同一游戏目录

### 4. 确认起点干净

在**没装过 HMM 的状态**下开始，或先完整卸载旧版本。残留的应用数据会让首启引导、
数据库初始化、迁移这些路径测不到真实行为。

## 二、测试时的通用纪律

### 一次只改一个变量

出现异常时立即停下记录，不要"再点几下看看会不会好"。连续操作会让日志里的因果关系断掉，
事后无法判断是哪一步触发的。

### 每个异常都记四件事

```text
操作步骤：点了什么、顺序如何
预期：应该发生什么
实际：实际发生什么
时间戳：几点几分（用于在日志里定位）
```

**时间戳最重要**。日志按时间排列，没有它我无法把你描述的现象对应到日志条目。

### 截图时机

- UI 异常：立刻截图，别等切走页面
- 错误提示：连带上下文一起截，只截弹窗看不出是哪个操作触发的
- 截图前确认画面里没有你的真实用户名、存档路径、Steam 账号

### 高风险操作前后各看一次游戏目录

C 章节（Mod 生命周期）和 D 章节（存档）每一项，操作前后都用文件管理器对比一次目录内容。
日志能告诉我程序**以为**它做了什么，只有实际目录能告诉我它**真的**做了什么。这两者不一致
正是最危险的 bug 类型。

## 三、几个容易测漏的点

### A6：控制台窗口

release 构建不应弹出额外控制台。这个只在**双击安装后的 exe** 时能测到，
从命令行启动看不出来。

### B3/B4：卸载清理

`installer.nsi` 已确认接入卸载前 hook，但**接入不等于执行成功**。卸载后要查：

- 任务管理器里无 `hmm-save-backup-worker.exe` 残留
- 计划任务里无残留条目（`taskschd.msc`）

### C3：路径穿越

需要**故意构造一个恶意包**：做个 zip，里面放 `../../evil.txt` 这样的条目。
正常 Mod 包测不到这条路径。程序必须拒绝，不能解压到游戏目录之外。

### C7：安装中断回滚

要真的中断 —— 安装过程中关掉程序或断电级别的强杀，而不是点"取消"。
点取消走的是正常取消路径，和崩溃后的恢复是两套逻辑。

### D3：Steam 多账户

只有机器上真有多个 Steam 账户目录时才测得到。如果只有一个账户，
这项记 `跳过` 并注明原因，不要记 `通过`。

### 存储目录迁移（#275）

设置页 → Mod 存储目录。要点：

- 库**非空**时才走迁移任务；库为空时只是改设置，两条路径都要测。
- 迁移完成不等于生效：进度条走完、提示「重启后生效」后，**导入 / 删除入口应处于禁用态**并给出原因；
  此时旧目录副本还在，属正常。重启后再看：新目录下 `sandboxes/` 有全部包、旧目录的 `sandboxes/`
  已清空、`%APPDATA%\dev.helsincy.modmanager\mod-import\migration.json` 不存在。
- 中途点「取消」：应回到未迁移状态，新目录里不留包目录（可留空 `sandboxes/` 与标记文件），导入入口恢复可用。
- 选择非空的外来文件夹、游戏目录内的文件夹、当前目录的子目录，都应被拒绝并给出具体原因，不应写入任何文件。
- 迁移进行中强杀程序（不是取消）：下次启动应自动回滚，App Log 有 `mod_storage_migration_settled`，
  库内容与迁移前一致。

### 移动导入（#275 ④）

设置页 → Mod 导入 → 「导入后删除原始压缩包」。**用可丢弃的 zip 副本测**，开启即会删文件。

- 开启时必须先出确认弹窗（点背景不关、焦点在取消）；取消后开关应保持关闭。
- 开启后导入一个放在下载目录的 zip：导入成功 toast 后，源 zip 应已消失，且没有额外警告 toast。
- 把 zip 放进游戏目录内再导入：导入成功，但源 zip **保留**，并出现「已导入，原始压缩包未删除」警告；
  Mod 存储目录、应用数据目录内同理。
- 导入失败（故意选一个坏 zip）：源文件必须原样保留。
- 关闭开关后再导入：源 zip 保留、无提示。

## 四、日志导出与提交

### 导出方式

日志 / 诊断页 → 「导出诊断包」→ 确认。

导出包内容（`export_support_diagnostics`）：

- 平台摘要
- 已脱敏 App / Debug / Task 日志
- 已校验 Audit 事件
- 健康聚合计数

导出成功的 toast 会显示各类日志的行数与事件数。**如果 Debug 日志行数是 0**，
说明第一步的开关没生效，这轮日志的诊断价值会大幅下降。

### 脱敏边界（这决定我能看出什么）

诊断包**默认脱敏**，按 `docs/LOGGING.md` 的规则，以下内容不会出现在包里：

- 完整本地路径（只有 `safe_path` / 相对逻辑路径如 `nativePC/...`）
- Windows 用户名与 home 路径
- Steam ID
- token / cookie / API key
- 真实存档内容、第三方 Mod 包内容

**这是设计意图，不是缺陷** —— 诊断包就是为了能安全外发。但你要知道由此带来的限制：

> 我能从日志判断"程序认为自己写了哪些逻辑路径、结果是什么、错误码是什么"，
> **不能**判断"它有没有写到你机器上的正确物理位置"。

所以「文件是否落到正确位置」这类项目，必须靠你实际看目录来判定，
日志只能作为辅证。这也是上面要求"操作前后各看一次目录"的原因。

### 提交给我时一并给出

1. 诊断包文件
2. 填好的验收清单（含 `跳过` 项的原因）
3. 异常现象的时间戳列表
4. 相关截图

有时间戳我才能把现象和日志条目对上；只有诊断包的话，我只能报告"日志里有哪些错误码"，
没法判断哪个对应你看到的问题。

### 导出本身会被审计

按 `docs/LOGGING.md` 的审计要求，「导出诊断包」是需要写 Audit Log 的操作。
所以你会在审计记录里看到导出事件本身，这是预期行为。

## 五、判定与后续

- P0 全通过 → 可以发布
- 任一 P0 失败 → 停止发布。把失败项 + 日志 + 时间戳给我，修完只需重跑受影响章节
- P1 失败 → 记为已知问题，写进 Release notes 的已知限制

不要把"应该能通过"写成"已通过"，也不要把"没测到"写成"通过"。
按 `docs/TESTING.md` 的记录约定，`已执行` / `未执行` / `风险` 三类分开写。
