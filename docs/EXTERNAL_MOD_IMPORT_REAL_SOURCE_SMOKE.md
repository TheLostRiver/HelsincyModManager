## 1. 目的与边界

T17 的全部自动化只使用临时目录和人工构造 fixture（设计文档「测试策略」章的强制口径）。这条边界
是对的，但它留下一个自动化永远无法回答的问题：**真实狩技盒子库的形状是否符合 adapter 的假设**。

本文固定这次人工 smoke 的前置、脱敏记录纪律、两趟执行步骤和逐条判定标准。它的产出是一段可
回填进设计文档的结论，不是新增测试。

本文不放宽任何安全边界：来源始终只读，不安装、不启用、不写游戏目录，不把真实路径、目录名、
Mod 名或 XML 原文写进任何记录、日志或诊断包。

## 2. 只有真实数据能证伪的假设

自动化已覆盖每条规则的正负分支，所以本 smoke **不重复验证规则本身**，只验证「真实库是否落在
规则覆盖的形状里」。需要证伪的假设：

| 假设 | 出处 | 若不成立的后果 |
| --- | --- | --- |
| 候选目录名只含 ASCII 数字 | 首个来源契约 | 非数字目录不会成为候选，玩家的一部分 Mod 直接看不到 |
| 每个候选形如 `files/` + `info.xml` | 首个来源契约 | 结构不符者落到 `structure_invalid`，无法导入 |
| 玩家常选安装根而不是 `Mods_582010` | Slice 5E | 自动下潜若不命中真实布局，选安装根会得到 0 候选 |
| 缺 `files/` 载荷是少数情况 | Slice 5E | `payload_missing` 若占比很高，玩家会看到一片不可导入项 |
| `info.xml` 字段限于 `moduleName`/`name`/`author`/`version`/`modType` | 元数据映射 | 真实字段变体会退化成占位名或 `metadata_invalid` |
| 真实库候选数远低于 `10,000` | Slice 1 定稿 | 触达 `max_total_candidates` 会只返回一个资源拒绝项 |

## 3. 硬前置与安全边界

- 执行前 `main` 处于干净状态，完整 `scripts/verify.ps1` 通过。
- 来源目录**只读**：不在 smoke 期间用任何工具修改、移动、重命名狩技盒子库。
- 全程不选择真实 MHW:I 游戏目录 —— T17 是 import-only，本 smoke 不需要配置游戏目录即可跑完
  扫描与预览；Pass B 的导入也不写游戏目录。
- 出现下列任一情况**立即停止**并记录：UI 显示任何完整路径、目录名或 XML 片段；来源完整性
  基线在结束时不一致；出现无法解释的后台任务；诊断导出里出现来源信息。
- Pass B 若选择在真实 HMM 安装上执行，先确认你接受把这批 Mod 留在库里（或事后手动删除）。
  当前桌面 AppData 没有测试隔离入口（见 CL0 验收基线的 G5），要完全隔离只能用一次性
  Windows 账户或 Windows Sandbox。

## 4. 记录纪律（脱敏口径）

**允许记录**：计数、比例、耗时、稳定状态码/reason code、页大小、来源完整性摘要（单个 hash）、
公开 task id/batch id 前 8 位。

**禁止记录**：来源根路径或其任何片段、候选目录名（编号也算，它是来源内标识）、Mod 显示名、
作者名、`info.xml` 原文或片段、内容指纹、`sourceFingerprint`、`selectionId`、截图中未打码的
上述内容。

截图如需保留，先遮盖 Mod 名与作者列；本文的结论只回填数字与状态码。

## 5. Pass A：真实全库只读扫描与预览（不导入）

目的：验证第 2 节的布局假设与状态分布。这一趟**不选择任何候选、不启动导入**。

### 5.1 来源完整性基线

在 PowerShell 中对来源根做一次基线摘要。只输出条目数与一个 hash，不输出任何名称：

```powershell
function Get-HmmSourceDigest {
    param([Parameter(Mandatory)][string]$Root)
    $full = [IO.Path]::GetFullPath($Root)
    $lines = Get-ChildItem -LiteralPath $full -Recurse -Force |
        ForEach-Object {
            $rel = $_.FullName.Substring($full.Length).TrimStart([IO.Path]::DirectorySeparatorChar)
            if ($_.PSIsContainer) {
                "{0}|dir" -f $rel
            } else {
                # 必须纳入内容 hash:仅凭长度与 mtime 无法证明内容未变——
                # 等长原地改写并回写 mtime 就能骗过前两者,而设计要求断言的是「内容未被修改」。
                $content = (Get-FileHash -LiteralPath $_.FullName -Algorithm SHA256).Hash
                "{0}|{1}|{2}|{3}" -f $rel, $_.Length, $_.LastWriteTimeUtc.ToString('o'), $content
            }
        } | Sort-Object
    $sha = [Security.Cryptography.SHA256]::Create()
    $hash = $sha.ComputeHash([Text.Encoding]::UTF8.GetBytes(($lines -join "`n")))
    [pscustomobject]@{
        EntryCount = $lines.Count
        Digest     = ([BitConverter]::ToString($hash) -replace '-', '').ToLowerInvariant()
    }
}

$before = Get-HmmSourceDigest -Root '<狩技盒子库根>'
$before   # 只把这两个数字记进结论
```

摘要**刻意逐文件计算内容 SHA-256**，因此对整库跑一次需要读完全部字节（参考量级：约 7,700 个文件 / 0.7 GiB 需数十秒）。这是必要代价——本节的判定标准是「来源内容未被修改」，只比对长度与 mtime 支撑不了这个结论。

摘要含相对路径、字节长度、mtime 和内容 hash，但**刻意不含 atime** —— 设计文档明确 atime 可能被
读取更新，不作为可保证字段；把它纳入会让「只读扫描」本身就制造出差异。

### 5.2 执行步骤

1. 启动应用，进入 Mod 管理页，点「从第三方管理器导入」。
2. 在原生目录选择器中选择**狩技盒子安装根**（不是 `Mods_582010`）。
3. 记录：来源显示标签是否为不含路径的通用标签；是否出现路径。
4. 启动扫描，记录 task id 前 8 位、phase 序列、扫描耗时。
5. 扫描完成后逐页翻完预览，记录每个 `previewStatus` 的计数与总候选数。
6. 关闭弹窗，重新打开并**直接选择 `Mods_582010`**，重复扫描。
7. 对比两次的候选总数与状态分布。

### 5.3 判定表

| 检查项 | 通过标准 |
| --- | --- |
| 自动下潜 | 选安装根与直接选 `Mods_582010` 得到**相同候选总数与相同状态分布** |
| 候选可见性 | 候选总数与你已知的盒子内 Mod 数量一致；差额能被状态码解释，不是静默丢失 |
| `payload_missing` 占比 | 记录实际比例。**≤10% 视为符合「少数情况」预期**；>30% 说明该状态需要更好的产品化处理，记为缺口而非失败 |
| `structure_invalid` | 每一项都能对应一个真实的结构异常（缺 `files/`、链接、非目录）；不能出现"看起来正常却被拒" |
| `metadata_invalid` | 记录数量。若非零，抽查其中一项确认 `info.xml` 确实超出解析限制 |
| `resource_limit_exceeded` | **不应出现**。若出现说明真实库候选数触达 10,000 上限，需重新评估预算 |
| 命名回退 | 不存在大批候选显示为脱敏占位名（说明 `moduleName`/`name` 映射未命中真实字段） |
| 引导文案时机 | 若候选总数 >50：翻到第 2 页前**不应**出现「无可导入」引导（这是 PR #264 修的行为，只有真实多候选库能验证） |
| 脱敏 | UI、Task Log、诊断导出中均无路径、目录名、XML 片段 |
| 来源只读 | 结束后 `Get-HmmSourceDigest` 的 EntryCount 与 Digest 与基线**完全一致** |

## 6. Pass B：受控子集完整导入闭环

目的：验证导入、取消、重试、幂等在真实内容上的行为。**只用小子集**（建议 3–5 个候选）。

### 6.1 环境

二选一，先记明用了哪个：

- **隔离**（推荐首次）：Windows Sandbox 或一次性 Windows 账户，把 3–5 个真实候选目录**复制**
  进去构成一个最小盒子库。复制保留结构与 `info.xml` 内容，这正是要验证的部分。
- **真实安装**：直接在日常 HMM 上导入 3–5 个候选。更贴近实际迁移，但这批 Mod 会进入你的
  真实库，需要你接受保留或事后删除。

### 6.2 执行步骤

1. 扫描 → 选中 3–5 个 `ready` 候选 → 启动导入 → 记录结果分页的逐状态计数。
2. **取消**：重新扫描同一来源，**只选中步骤 1 那同一组 3–5 个候选**（绝不用「全选」），
   启动后立即取消。记录已成功项是否保留、未开始项是否为 cancelled、来源摘要是否仍与基线一致。

   > 这里必须限定范围。在真实安装上执行时「全选」等于整个来源库，取消一旦没赶上就是一次
   > 非预期的全库导入；而已导入批次现在是**永久保留**的，产生的记录清不掉。
3. **幂等**：再次扫描同一来源。预期先前成功的候选变为 `already_imported` 而非 `ready`。
4. **重试**：若出现任何 `failed` 且 `retryable`，执行重试，记录新 task id 与最终计数。
5. 打开被导入 Mod 的详情面板，检查「来源」行。

### 6.3 判定表

| 检查项 | 通过标准 |
| --- | --- |
| 导入成功 | 选中项全部进入 imported；结果页逐状态计数之和等于总数 |
| 内容正确 | 抽查一个导入结果，其文件数与来源候选 `files/` 下的文件数一致 |
| 取消语义 | 已成功项保留、未开始项 cancelled、无残留临时目录 |
| 幂等 | 二次扫描中先前成功项为 `already_imported`，重复导入不产生副本 |
| 详情来源行 | 显示 adapter 显示名 + 导入时间；**不含**路径、指纹、batchId |
| 不触碰游戏目录 | 全程未要求配置游戏目录，游戏目录字节未变（若已配置，做一次前后对比） |
| 来源只读 | 每一步结束后来源摘要与基线一致 |

## 7. Slice 5 导入记录与保留期

1. 关闭导入弹窗，从工具栏的记录入口重新打开 —— 应直接进入记录视图，**不拉起原生目录选择器**。
2. 记录列表是否包含 Pass A 的只扫描批次与 Pass B 的导入批次，时间/状态/计数是否与当次一致。
3. 展开一个批次的明细，确认逐项显示**候选 Mod 名**而不是内部候选 ID。
4. 确认界面明示保留期上限与「不能从历史重试」。
5. 分页：若批次数 >20，翻页应不重不漏。

## 10. 已知不可覆盖项

即使本 smoke 全通过，下列仍未被验证，不要据此宣称完整覆盖：

- **大小写等价库目录冲突**：`Mods_582010` 与 `mods_582010` 并存只在大小写敏感文件系统上可能，
  NTFS 默认造不出来。该分支由 CI 的 Linux runner 覆盖（PR #264 新增用例），Windows 上永远走跳过路径。
- **历史「空页 + 非零总数」守卫**：后端 COUNT 与分页同事务，正常后端无法自然触发，只有单测覆盖。
- **10,000 候选上限与资源预算**：真实库达不到该量级，仍只有人工基准覆盖。
- **其他第三方来源**：只有 `hunting_box_directory_v1` 一个 adapter；其他来源必须另加 adapter 与
  fixtures，不在本文范围。
