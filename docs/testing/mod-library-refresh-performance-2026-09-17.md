# Mod 安装／卸载后的列表刷新性能采样

2026-09-17 同机 Windows WebView2 对照表明：修复版在单项与批量安装／卸载中保留现有卡片和滚动位置，
操作结束后只进行一次列表查询和一次恢复扫描。这证明首轮修复改善了清屏与重复同步，整体性能尚未
验收完成。20 项批量安装从启动请求到列表同步完成的中位耗时由 18.04 秒降到 8.08 秒，其中约
7.78 秒发生在收到任务终态之前，约 0.30 秒用于终态后的列表同步。以下结果来自隔离人工数据，
不是玩家实际 Mod 库的耗时承诺，也未证明 100 项库或 100 项批次满足性能要求。

后续已完成 release 的 20／100 项、阶段计时及原生进程查询原型对照，见
[追加扩展性评估](mod-library-release-scale-evaluation-2026-09-17.md)。以下保留首轮 dev 的方法与结果，
不同构建模式和库规模的数字不可直接混用。

第二轮产品已进一步替换原生进程检测并拆分状态缓存，正式 release 的 36 个样本及剩余批量成本见
[第二轮产品复测](mod-library-incremental-state-performance-2026-09-17.md)。下文缓存缺口和待实施方向
记录的是首轮修复当时的边界。

## 版本与环境

- 基线：`42f2d9e4129e329f0e0afee932aa26685d2f3bdf`。
- 修复：`d3861c32`（`fix: 优化 Mod 安装卸载后的列表刷新`）。
- Windows x64，AMD Ryzen 7 5800H（8 核／16 线程），WebView2 `153.0.4234.32`。
- 两个版本均使用仓库默认 dev profile；workspace crate 未优化，依赖按既有配置优化。
- 使用不同的临时应用 identifier 隔离 AppData，游戏目录分别位于各自 Sandbox 内；前端均由 Vite 提供。
- 相同尺寸的实际 Tauri 窗口，20 张卡片同页显示。使用真实页面按钮，执行生产用例及文件事务。

采样构建只通过进程级 `TAURI_CONFIG` 覆盖应用 identifier，通过 `HMM_SANDBOX_DATA_DIR` 指向对应
隔离根；没有修改产品配置或引入新的生产路径能力。WebView2 调试端口按本机可用范围选择。

## 数据与步骤

人工库包含 20 个 Mod，每项 8 个 512 KiB 文件，共 80 MiB。文件分布在互不重叠的
`nativePC/models/perf-XX/` 下。每个 Mod 有一个预先存在、内容不同的目标文件，用于验证覆盖备份和
卸载还原；另有未归属 sentinel 及人工前置文件。全程不使用第三方 Mod、真实游戏或存档。

两个版本各预热一次 20 项安装；随后依次测试单项、5／10／20 项批量，每种数量按
“卸载 → 安装”重复三次，共 48 个正式样本。每次安装结束时均为 20 项已安装；卸载 N 项后剩余
20−N 项已安装。预热、启动、预览／封存、操作之间的等待及收尾卸载不计入表中时间。

通过 WebView2 CDP 注入观察探针：

1. 在 IPC fetch 发出 `start_install_task`、`start_uninstall_task` 或 `start_batch_mod_lifecycle`
   时记录起点；不记录请求正文、headers 或 token。
2. 从真实 `hmm://task-progress` 事件记录任务终态；这段时间包含启动用例、执行及终态传递，并非纯文件复制时间。
3. 等待本轮列表相关 IPC 完成、卡片数量恢复为 20 且列表 `aria-busy=false`，在下一帧记录列表同步结束。
4. 再观察 800 ms，确认没有迟到的重复请求；这段稳定等待不计入耗时。关闭批量结果弹窗的时间也不计入。
5. 使用 MutationObserver／动画帧记录卡片节点是否仍连接、最少卡片数和滚动位置。每 50 ms 串行请求
   原生窗口 `innerSize`，观察宿主响应往返时间。

修复版先运行，原版随后运行；没有人为清空 OS 文件缓存。下表采用各组三次的中位数，不报告小样本 p95。
各列独立取中位数，因此阶段中位数之和可能与总时间中位数略有差异。

## 剩余耗时的日志核对

对原始 48 个样本进行只读关联：由真实终态事件找到父任务 Task Log，再用该版本
`TaskManager::generate_task_id` 编入任务 ID 的创建时间，与隔离 fixture 的逐项成功 Audit Log
时间戳对应。每个样本均核对到预期数量的成功条目，子任务区间没有交叠。

20 项安装的三次中位数如下，单位为毫秒，各列独立取中位数：

| 区间 | 原版 | 修复版 |
| --- | ---: | ---: |
| 父任务创建 → 首个子任务创建 | 686 | 441 |
| 各子任务创建 → 成功 audit 时间戳，累计 | 7431 | 6528 |
| 上一条目成功 audit 时间戳 → 下一子任务创建，累计 | 8600 | 732 |
| 最后条目成功 audit 时间戳 → 父任务终态日志 | 25 | 21 |

该核对支持两个判断：条目之间重复处理的开销已经大幅下降；剩余耗时主要位于各单项执行内部。
子任务区间包含规划、前置条件复核、写入准入和文件事务等工作。成功 audit 的时间戳在写日志之前
取得，后续 audit 写入、任务收尾、batch journal 与下一项 facts 读取落在后面的区间内。
这些区间不能进一步归因为复制、hash、备份、刷盘或锁等待。现有批量 Task Log 只有父终态，
`durationMs=0` 也不能用于这种分摊；后续必须增加阶段计时或使用 profiler。

该关联使用当前源码中任务 ID 的具体实现，仅用于复核这次人工实验，不新增对任务 ID 格式的产品契约。
Task Log 和 audit 使用墙钟，浏览器使用单调计时；不能将两种绝对时间直接相减。

## 缓存仍存在的结构缺口

当前实现保留了展示快照，但 `modLibrarySessionStore.ts` 仍在一组写入开始和结束时清空所有可信
页面与状态快照。`modLibraryPageLoader.ts` 仍等待「当前页 IDs ∪ 写任务目标 IDs」的恢复扫描后，
才提交可信页结果。目录数据、安装状态及文件完整性在这条刷新链上仍耦合，按页查询不意味着底层
没有全局元数据读取。首轮修复不是完整的增量状态缓存方案。

后续调整应保留已验证的请求合并、展示保持与后台查询，按以下边界推进：

1. 目录信息和安装状态分别缓存；以游戏实例、profile、Mod 身份及版本绑定状态。一次局部写入只更新
   受影响的状态；涉及安装状态的筛选页需要重新计算条目与计数，不能仅修改卡片标签。
2. 单项事务持久化完成后，由后端提供有版本的已提交状态摘要，批量逐项合并。前端不能根据点击、
   普通 task completed 事件或旧缓存自行认定写入成功；事件遗漏或乱序通过版本化快照补齐。
3. 将已提交安装状态与文件完整性检查结果区分。恢复记录、失败／回滚和证据降级立即影响相应状态；
   完整性扫描按启动、外部变化或显式校验需要运行，不再成为每次更新卡片的整页前置条件。后端写前
   的 InstallPlan、归属、backup、manifest、rollback/recovery 和同游戏串行约束继续成立。
4. 对批量执行分别计时 runtime 准备、整批与逐项 facts、规划、读文件／hash、备份、提交／持久化、
   journal／audit 和状态发布。先证实占比，再决定哪些准备工作可以复用，哪些读取可以缩小范围。

这部分是待实施的调整方向，不能当作当前分支已经具有的能力。

## 后续性能验收

需要分开验证两个问题：

- **库中有 100 个 Mod，操作其中 1 个：** 固定操作文件和既有安装数量，只增加目录项，检查无关
  条目是否增加查询／扫描工作；再增加既有安装数量，检查全局事实读取的扩展性。未改变卡片应保留，
  已提交状态不应等待无关 Mod 的文件内容校验。
- **一次操作 100 个 Mod：** 在固定每项文件规模下测量 20／100 项安装与卸载，把必要文件事务、
  重复准备和列表同步分别记录，并检查每项完成后的状态更新。总时间不能脱离文件数、字节数和备份
  情况承诺，也不能从现有 20 项结果线性外推。

首轮未覆盖实际 release 桌面构建及预览／封存的独立耗时；上述补测现已记录在
[追加扩展性评估](mod-library-release-scale-evaluation-2026-09-17.md)，整体性能仍未验收。
验收同时看绝对耗时、工作量增长、卡片稳定和状态更新延迟，不只看相对原版的改善比例。

## 完整性与边界

- 所有正式操作均返回 `completed`，没有失败或取消样本混入统计。
- 两个版本分别通过 GUI 批量卸载收尾；游戏目录最终 28 个文件的路径、大小和 SHA-256 均与各自
  初始基线完全一致，包括原有目标和未归属 sentinel。
- 修复代码已通过完整 `scripts/verify.ps1`，包含 1162 项前端测试和 Rust 常规测试／静态检查。
- 本报告首轮未采样 release 包、真实玩家 Mod、缩略图负载、冷文件缓存、持续外部文件变动或跨进程竞争。
  80 MiB 人工库复现了卡片清空和重复同步，但未复现用户实际库的精确 4–5 秒；不能据此承诺统一秒数。
- 原始时间线、采样探针、构建日志和人工数据保持为本地实验产物，不加入版本管理。
