# Mod 安装／卸载后的列表刷新性能采样

2026-09-17 同机 Windows WebView2 对照表明：修复版在单项与批量安装／卸载中保留现有卡片和滚动位置，
操作结束后只进行一次列表查询和一次恢复扫描。20 项批量安装从启动请求到列表同步完成的中位耗时由
18.04 秒降到 8.08 秒。以下结果来自隔离人工数据，不是玩家实际 Mod 库的耗时承诺。

## 版本与环境

- 基线：`42f2d9e4129e329f0e0afee932aa26685d2f3bdf`。
- 修复：`d3861c32`（`fix: 优化 Mod 安装卸载后的列表刷新`）。
- Windows x64，AMD Ryzen 7 5800H（8 核／16 线程），WebView2 `153.0.4234.32`。
- 两个版本均使用仓库默认 dev profile；workspace crate 未优化，依赖按既有配置优化。
- 使用不同的临时应用 identifier 隔离 AppData，游戏目录分别位于各自 Sandbox 内；前端均由 Vite 提供。
- 相同尺寸的实际 Tauri 窗口，20 张卡片同页显示。使用真实页面按钮，执行生产用例及文件事务。

采样构建只通过进程级 `TAURI_CONFIG` 覆盖应用 identifier，通过 `HMM_SANDBOX_DATA_DIR` 指向对应
隔离根；没有修改产品配置或引入新的生产路径能力。WebView2 调试端口按本机可用范围选择。

## 数据与步骤

人工库包含 20 个 Mod，每项 8 个 512 KiB 文件，共 80 MiB。文件分布在互不重叠的
`nativePC/models/perf-XX/` 下。每个 Mod 有一个预先存在、内容不同的目标文件，用于验证覆盖备份和
卸载还原；另有未归属 sentinel 及人工前置文件。全程不使用第三方 Mod、真实游戏或存档。

两个版本各预热一次 20 项安装；随后依次测试单项、5／10／20 项批量，每种数量按
“卸载 → 安装”重复三次，共 48 个正式样本。每次安装结束时均为 20 项已安装；卸载 N 项后剩余
20−N 项已安装。预热、启动、预览／封存、操作之间的等待及收尾卸载不计入表中时间。

通过 WebView2 CDP 注入观察探针：

1. 在 IPC fetch 发出 `start_install_task`、`start_uninstall_task` 或 `start_batch_mod_lifecycle`
   时记录起点；不记录请求正文、headers 或 token。
2. 从真实 `hmm://task-progress` 事件记录任务终态；这段时间包含启动用例、执行及终态传递，并非纯文件复制时间。
3. 等待本轮列表相关 IPC 完成、卡片数量恢复为 20 且列表 `aria-busy=false`，在下一帧记录列表同步结束。
4. 再观察 800 ms，确认没有迟到的重复请求；这段稳定等待不计入耗时。关闭批量结果弹窗的时间也不计入。
5. 使用 MutationObserver／动画帧记录卡片节点是否仍连接、最少卡片数和滚动位置。每 50 ms 串行请求
   原生窗口 `innerSize`，观察宿主响应往返时间。

修复版先运行，原版随后运行；没有人为清空 OS 文件缓存。下表采用各组三次的中位数，不报告小样本 p95。
各列独立取中位数，因此阶段中位数之和可能与总时间中位数略有差异。

20 项全部卸载后已无受管 Mod 文件需要复核，因此它的列表同步时间比部分卸载短；不能将这些不同的
剩余文件量直接用作扫描算法的复杂度比较。批量逐项准备工作减少另由 5／10／20 项计数测试覆盖。

单项安装三次列表同步范围：原版 1130.8–1340.1 ms，修复版 268.8–275.8 ms。
20 项安装三次范围：原版 1362.6–1403.9 ms，修复版 292.3–300.8 ms。

## 卡片、滚动与调用次数

| 指标 | 原版 | 修复版 |
| --- | --- | --- |
| 24 个正式操作中的最少卡片数 | 每次降为 0 | 每次保持 20 |
| 原有卡片 DOM 节点 | 每次全部断开 | 每次全部保留 |
| 操作前后滚动位置 | 每次发生变化 | 每次保持 240 px |
| 单项安装的 query / manifest / recovery IPC 次数 | 3 / 4 / 4 | 1 / 0 / 1 |
| 单项卸载的 query / manifest / recovery IPC 次数 | 4 / 5 / 5 | 1 / 0 / 1 |
| 批量的 query / manifest / recovery IPC 次数 | 通常 4 / 4 / 4 | 每次 1 / 0 / 1 |

原版一个 10 项安装样本为 4 / 3 / 3：启动后 23.1 ms 发出的一次列表查询返回错误，另外的查询和最终
同步成功。该样本保留在统计中；修复版 24 个样本未观察到 IPC 错误。其余批量样本均为 4 / 4 / 4。
两个版本的批量结果查询均为
每次一次。这里统计启动之后的前端 IPC，不包含预览阶段或 runner 内部的事实读取；原版带 gameId
的 manifest 状态查询本身也会调用恢复扫描，不能把它当作单纯的 manifest 元数据读取。

整个操作及同步区间的窗口请求往返峰值：原版 778.1 ms，修复版 224.0 ms；修复版批量场景最高
23.4 ms。只看与终态后同步区间相交的窗口请求，原版峰值为 778.1 ms，修复版为 23.4 ms。该指标
支持阻塞查询移出宿主回调后的响应改善，不代表每个系统交互都零延迟。

## 完整性与边界

- 所有正式操作均返回 `completed`，没有失败或取消样本混入统计。
- 两个版本分别通过 GUI 批量卸载收尾；游戏目录最终 28 个文件的路径、大小和 SHA-256 均与各自
  初始基线完全一致，包括原有目标和未归属 sentinel。
- 修复代码已通过完整 `scripts/verify.ps1`，包含 1162 项前端测试和 Rust 常规测试／静态检查。
- 本轮未采样 release 包、真实玩家 Mod、缩略图负载、冷文件缓存、持续外部文件变动或跨进程竞争。
  80 MiB 人工库复现了卡片清空和重复同步，但未复现用户实际库的精确 4–5 秒；不能据此承诺统一秒数。
- 原始时间线、采样探针、构建日志和人工数据保持为本地实验产物，不加入版本管理。
