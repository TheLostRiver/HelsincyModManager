# Mod 管理第二轮产品复测：原生进程检测与增量状态

第二轮产品实现 `c5d76808` 已将 Windows `tasklist` 替换为原生进程快照，并拆开目录缓存、已提交
安装状态和文件完整性结果。在同机人工 release 场景中，100 张卡片同页的单项安装，末尾列表同步
中位数由 1137.9 ms 降到 18.0 ms；普通安装／卸载不再发起目录查询或整页恢复扫描，批量逐项更新卡片。

这解决了本轮覆盖的卡片刷新等待，未使批量文件事务瞬间完成。100 项、400 MiB 的批量安装，启动到
列表同步中位数为 16.984 秒，计入预览／封存为 23.713 秒；三轮仍有明显波动。下面同时保留执行、
同步、首项显示和准备阶段的耗时，不把几十毫秒的同步时间当作用户操作的总等待。

## 版本与实验边界

- 本次产品代码：`c5d768086b8bfe9b04e58647f4900663c12b2861`，分支 `hy/mod-refresh-performance`。
- 对照为首轮产品 `d3861c32` 的未插桩 release；原始数据及方法见
  [实施前扩展性评估](mod-library-release-scale-evaluation-2026-09-17.md)。没有将诊断原型作为产品基线。
- 本次使用 release、`tauri/custom-protocol`、打包前端和隔离应用标识；没有 Rust 阶段插桩。
  可执行文件 SHA-256 前 12 位为 `31915F5D4E6A`，完整指纹与原始样本留在 ignored 实验目录。
- Windows x64、AMD Ryzen 7 5800H、WebView2 `153.0.4234.32`，与前期同一机器和人工 fixture。
- 库固定为 100 个 Mod，每项 8 个 512 KiB 文件；每项 4 MiB，全部共 400 MiB。每项一个目标预先存在
  不同内容，安装需备份、卸载需恢复；另有不归属 Mod 的 sentinel 和人工前置文件。
- 沿用已有人工数据，没有重建 fixture、替换基线、使用真实游戏、第三方 Mod 或玩家存档。
- 每个场景／数量按「卸载 → 安装」重复三次。正式样本 36 个；安装预热、补齐到 100 项、清理和运行
  阻断检查单独保存。采样时没有并行编译或跑测试。

| 库中 Mod 数 | 每轮结束时已安装数 | 页容量／实际卡片数 | 操作数量 | 正式样本 |
| ---: | ---: | --- | --- | ---: |
| 100 | 20 | 192／100 | 1、20 | 12 |
| 100 | 100 | 192／100 | 1、20、100 | 18 |
| 100 | 100 | 24／24（默认） | 1 | 6 |

各表为三次中位数。每轮安装开始前已先卸载选中项，表中的「已安装数」指往返结束时的数量。
OS 文件缓存未清空，旧、新版本分时运行，没有控制全部系统负载；不能把整批总差值全部归因于
进程 API，也不能从这三次采样推导用户级 p95 或不同机器的保证时间。

## 实现及安全边界

1. Windows 使用 Tool Help 快照和精确映像名匹配。每次写入前重新查询；快照／枚举错误重试三次后
   返回 `Unknown`，只有正常枚举耗尽才是 `NotRunning`，不复用批次开始时的「未运行」。
2. 后端轻量状态只读 manifest、普通 recovery、reinstall transaction；服务没有游戏文件或备份
   内容读取能力。每次重新读持久化元数据，以 scope、epoch、revision 排序，并包含共享归属变化
   影响的其他 Mod。单项终态前和批量每项执行／记账尝试后发布实际状态，通知不授权写入。
3. 前端按 Mod 合并状态，展示更新不推进目录查询 generation。安装／卸载保留目录页；每轮终态
   补读当前页、保留页和任务目标，修复漏事件。状态筛选仍重新查询成员、总数和夹紧页码。
4. 完整性扫描独立保留。普通元数据不能清除已知异常，跨写入的旧扫描不能回填；显式刷新、详情的
   完整性查询和恢复中心继续执行扫描。查询失败、未同步或 unsafe 状态继续阻断相应写入口。

InstallPlan、manifest、backup、rollback/recovery、同游戏／profile 串行、写前实时校验和审计继续
执行。本轮没有减少 fsync、合并恢复记录持久化或改变事务顺序。

## 计时口径

- **执行：** 发出 `start_*` IPC 到收到任务终态，包含启动、后端执行和终态传递。
- **末尾同步：** 终态到相关查询完成、卡片数量正确且 `aria-busy=false` 的下一次前端观测。
- **启动到同步：** 上述两段总时间。
- **首项卡片更新：** 发出 `start_*` 到首个选中卡片的 `data-status` 变成实际结果；原卡片一直保留。
- **含预览／封存：** 每个样本的预览 IPC、封存 IPC、启动到同步相加后再取中位数，不包含人工选择、
  确认思考或步骤之间的等待。各列独立取中位数，不能直接相加各列得到总中位数。

卡片时间由 MutationObserver／requestAnimationFrame 观测 DOM，未测屏幕像素实际呈现时间。额外
观察同步后 800 ms 以捕获重复请求，这段等待不计入耗时。计时探针只在实验进程中注入，没有加入产品。

## 逐项更新、缓存与响应

- 全部 36 个正式任务均 `completed`，合计 858 次逐项状态变更；每次收到预期数量的状态事件，
  每个选中卡片最终状态与 manifest 安装集合一致。所有批量的首项卡片均在父任务终态前更新。
- 每次操作的原有卡片 DOM 节点全部保留，最少卡片数为该场景的 100 或 24，滚动位置保持 240 px。
- 从 `start_*` 之后到同步后观察结束，`query_mod_library`、`scan_install_recovery` 和带扫描语义
  的 `get_install_manifest_status` 调用均为 0；`get_mod_installation_states` 每次恰好 1 次。
  批量结果读取每次 1 次。这里统计前端 IPC，后端必要写前检查继续存在。
- 858 次状态变更中，实验监听器收到状态事件到 DOM 属性更新的观测最大延迟为 6.4 ms。这不包括
  后端持久化到发布、事件传输或显示器呈现，不能当作完整提交到像素的延迟保证。
- 100 项安装首项卡片在启动后中位 1.672 秒更新；计入预览和封存，同一指标为 8.384 秒。20 项
  安装对应为 0.567 秒和 2.138 秒。准备阶段仍会延迟首项完成，原卡片在此期间保持显示。
- 批量执行区间窗口 `inner_size` IPC 往返峰值为 16.9 ms；与终态后同步相交的请求峰值为 44.2 ms。
  全样本最高为 396.1 ms，发生于一次默认分页的单项安装，覆盖启动请求约 45.8–441.9 ms 的区间，
  启动回复在 434.5 ms 返回，早于终态 641.2 ms。现有单项启动入口仍有同步准备工作；这条时间线
  定位到启动阶段，但没有证明某个内部函数独自造成全部延迟，不能宣称全流程已无 UI 阻塞。

## 波动及后续边界

保留全部三次原始百项结果，单位为秒；没有删掉较慢轮次后重算。

| 操作／口径 | 第 1 次 | 第 2 次 | 第 3 次 |
| --- | ---: | ---: | ---: |
| 安装：启动到同步 | 15.067 | 16.984 | 23.452 |
| 安装：含预览／封存 | 21.765 | 23.713 | 31.429 |
| 卸载：启动到同步 | 9.479 | 9.703 | 11.325 |
| 卸载：含预览／封存 | 12.692 | 13.117 | 14.914 |

本次没有 Rust 阶段插桩，不能将 23.452 秒的慢轮归因到某一次 fsync。前期诊断已发现持久化波动和
重复准备成本，详见实施前报告。本次百项安装预览中位 2.664 秒、封存 4.103 秒；卸载为 1.047 秒和
2.343 秒。它们没有因列表缓存解耦而消失。

本轮有证据支持普通状态同步摆脱整页扫描依赖，以及批量完成项及时更新；没有证据宣称整个批量
执行性能已达标。后续应分别处理启动阶段的同步准备、预览／封存的重复事实读取和文件事务成本。
任何准备结果复用都需绑定可验证版本；持久化组织调整仍需覆盖崩溃、manifest 失败、回滚失败和重启
恢复，不能为了减少总秒数跳过写前复核、备份或恢复记录。

## 验证与收尾

- 完整 `scripts/verify.ps1` 实际通过，包含 1177 项前端测试、2638 项 Rust 测试以及
  policy、文档链接、secret、格式、typecheck、lint、build、cargo check／clippy。
- 随后自审补齐组合替换的状态发布、移除失效 helper 并迁移测试、纳入详情页旧扫描入口的完整性
  结论。最终相关复验通过：前端 1175 项全部通过、typecheck／lint／build、Tauri DTO 测试和
  `cargo clippy -p hmm-tauri --all-targets -- -D warnings`、Rust format。测试数量变化来自死代码
  测试迁移及新增回归，没有跳过失败用例。没有因这些边界内小修重复完整验证。
- 原生检测 15 项、轻量状态 10 项、batch 聚焦 106 项通过；包含批次第二项前游戏变为
  `Running`／`Unknown` 后禁止后续真实写入、保留首项结果，以及记账失败仍发布实际状态。
- release 两项 UI 负测通过：人工同名游戏进程运行时，安装和卸载均失败关闭。卸载前后 909 个、
  安装前后 109 个 game／backup／manifest／recovery 文件的路径、大小、SHA-256 及安装集合相同。
- GUI 卸载全部 100 项后，游戏目录的 108 个初始文件按路径、大小和 SHA-256 精确还原。
  应用和两次人工 helper 都按路径与启动时间核对身份后停止，实验 CDP 端口无监听。
- 原始样本校验通过：36 个唯一任务、同一构建指纹、调用次数、卡片／滚动、逐项状态、安装集合、
  计时关系及两项负测全部满足断言。构建、探针、原始样本、日志和人工数据保留在 ignored 目录。
- 未覆盖真实玩家 Mod、真实游戏运行、冷 OS 缓存、不同硬件／磁盘／Windows、持续外部变化或实际
  内核 API 故障注入。本次桌面采样未人为丢弃／重排事件，相关行为由聚焦回归验证。
